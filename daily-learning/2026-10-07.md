# Incident 1 - Docker Spring Boot Application Failed

## Symptom

The `order-app` container started with `docker run`, but the Spring Boot application failed during startup.

## Error

The application reported:

`Driver com.mysql.cj.jdbc.Driver claims to not accept jdbcUrl, ${DB_URL}`

## Investigation

1. Checked the container status.
2. Checked application logs.
3. Found that Spring Boot was failing during database initialization.
4. Checked the environment variables inside the container.
5. `DB_URL`, `DB_USERNAME`, and `DB_PASSWORD` were missing.
6. Checked the application configuration and confirmed it expects these variables.
7. Checked how the container was created.
8. Found that the container had been started using `docker run` instead of Docker Compose.
9. The project's `docker-compose.yml` already contained the required environment configuration.

## Root Cause

The application container was created directly with `docker run`, so the environment variables defined in `docker-compose.yml` were not applied.

## Fix

Removed the manually created container and started the application using:

`docker compose up -d`

Docker Compose then created the application and database with the required environment variables, network, volume, and healthcheck configuration.

## Verification

Verified that the container received:

- DB_URL
- DB_USERNAME
- DB_PASSWORD

Verified both `order-app` and `order-db` were healthy.

Verified:

`curl -i http://localhost:8081/api/orders`

returned HTTP 200 with order data.

## Troubleshooting Pattern

SYMPTOM -> LOGS -> CHECK RUNTIME CONFIGURATION -> CHECK HOW CONTAINER WAS CREATED -> FIX -> VERIFY

## What I Learned

Having configuration in a Docker Compose file does not mean every Docker container automatically uses that configuration. The container must actually be created through Compose for Compose configuration such as environment variables, networks, volumes, and dependencies to be applied.

## Interview Explanation

The application failed because it was started with `docker run` without the database environment variables. I checked the logs, found `${DB_URL}`, inspected the container environment, confirmed the variables were missing, and then identified that the container had been created outside Docker Compose. I recreated it with Docker Compose and verified the API returned HTTP 200.
